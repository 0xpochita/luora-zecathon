## What works

1. **ZIP 318 migration label** (`zip318_tx`, WASM + CLI `luora-z zip318`). Builds a `Zip318Evidence` from public data only and calls
   librustzcash's `zcash_protocol::zip318::classify` at the pinned rev `8672a4b2` (nothing re-implemented).
   - `source_actions` = Orchard actions, `destination_actions` = Ironwood actions (0 when no bundle).
   - `other_bundles_present` = any transparent input/output, Sapling spend/output or JoinSplit.
   - `sole_destination_value` = `-valueBalanceIronwood` when the Ironwood bundle has exactly 1 action and value enters it.
     This is the public crossing amount. If the single Ironwood action's spend were a real note (ZIP 318 says it is not),
     the output would be larger, but the amount crossing the turnstile, which is what ZIP 318's value collision is about, is still this one.
   - `expiry_is_canonical` = `PoolMigrationConstants::is_canonical_expiry_value` (height independent). Why not the strict
     `is_canonical_expiry(expiry, mined_height)`: ZIP 318 computes the expiry from the *scheduled* broadcast height, and pre-signed
     transfers are often mined in the next 34,560-block period. In blocks 3,523,700–3,526,699 many canonical-looking crossings mined after
     height 3,525,120 still carry expiry 3,559,680. The strict form would call all of them nonconforming; the library documents the value form
     for exactly the "no authoritative reference height" case, and it stays stable when a pasted transaction is later mined.
     The reason text still shows the canonical expiry for the mined (or tip) height.
   - `fee_is_canonical` = fee (sum of shielded value balances; only when no transparent part) == ZIP 317 conventional fee at that height
     (ZIP 318: "the canonical fee (provisionally the ZIP 317 minimum fee)").
   - `source_is_send_to_self` and `anchor_on_grid` stay `None` (viewing key / tree-state lookup); ZIP 318 treats unanswered as Unknown.
   - Constants: an observer implementor of `PoolMigrationConstants` with the ZIP defaults and `BlockSpacing::for_network` (NU7 spacing).
   - `classification`: `transfer` / `preparation` / `nonconforming` / `unknown`, or `not-a-migration-shape` when the transaction is v4,
     a coinbase, has no Orchard bundle, or is an ordinary Orchard-only transaction (no Ironwood and not 16 actions). The card is hidden then,
     so ordinary Orchard payments are never called "Fingerprintable".
   - UI: `MigrationCard` under the verdict: green **Blends in**, red **Fingerprintable**, neutral **Unknown**, the deciding reasons first,
     the rest folded, the library's "names a conformance class, never a provenance" wording, and an Ask AI button (it passes a
     `Check`-shaped summary to the existing `checkSubject`; Ask AI was not changed).
2. **NU7 readiness.**
   - Verified in the pinned source: Testnet NU7 at 4,465,026 (`zcash_protocol/src/consensus.rs:601`), Mainnet `None` (`:567`),
     branch ID `0x77190AD9` (`:883`, `:931`).
   - New check `nu7-shielded-budget` (ZIP 218 "Shielded pool action limits"): 330 Orchard actions, 330 Ironwood actions, 300 Sapling
     spends+outputs, 0 JoinSplits, shared budget 330 (Orchard + Ironwood + Sapling + 2·JoinSplits). Mirrors Zebra `c76a8677`
     `zebra-consensus/src/block.rs:191-197` constants, `:252` `ShieldedActionCounts::exceeded_limit` (same order, so the same message),
     and the mempool rejection at `zebra-consensus/src/transaction.rs:491` (`TransactionError::TooManyShieldedActions`, zebra#11529).
     These are per-block limits; a single transaction over them can never be mined, which is why the mempool refuses it. `na` before NU7.
   - `check_tx_at_nu7(hex, network, tipHeight, inputs) -> { height, hypothetical, upgrade, checks }`. Testnet: the real activation
     height, `hypothetical: false`. Mainnet: **chosen option: evaluate, labelled**. NU7 has no Mainnet height (librustzcash #3171), so the
     rules run on Mainnet parameters with NU7 activating at tip + 1 (`Net::MainWithNu7At`), and the Rules view says so under the
     selector. Reason: disabling it on Mainnet would remove the question exchanges actually have ("is my transaction shape still valid
     after NU7?") and every Mainnet sample; using Testnet parameters would mix in Testnet heights (ZIP 257 window, ZIP 2009). Regtest
     (NU7 off here) gets the option disabled.
   - Rules view: "Check at NU7" button next to "Check at" plus an `at NU7 …` option in the selector.
   - Demo: v4 sample `56b2017f…e54b` (height 1,000,000): green at its mined height, `version` fails at NU7 (ZIP 2003). Any v5/v6 Mainnet
     transaction fails `branch-id` at NU7 (needs `0x77190ad9`).
3. **Serialization round-trip** (`serialization-round-trip`): `Transaction::write` (`zcash_primitives/src/transaction/mod.rs:1183`)
   then byte compare; fail on a write error (the #3115 shape), on the first differing byte (the check carries `offset`, and the Rules row
   shows "Show byte N in Trace", which selects the deepest Trace row containing that byte), or on a txid change after re-reading
   (the #3137 shape). Passes on all ten real fixtures; no real failing transaction exists, so the fail paths are covered by review only.
